# Gate готовности RFC и ADR

## Статусы

- `закрыто` — данных достаточно для review;
- `частично` — данные есть, но утверждение или решение нельзя проверить полностью;
- `нет данных` — необходимой информации нет;
- `не применимо` — критерий не нужен выбранному профилю; укажи основание.

## Общий gate

| Критерий | Что проверить | Блокирует |
| --- | --- | --- |
| Предмет review | Понятно, какой decision, feedback или фиксация требуется | Да |
| Состояние документа | Понятно, проблема исследуется, решение предлагается или уже принято | Да |
| Проблема/context | Понятно, почему документ существует | Да |
| Цели и non-goals | Желаемый результат и границы не смешаны с решением | Да для proposal RFC |
| Источники | Факты, предположения и внешние выводы различимы | Да при спорных claims |
| Конфликты | Противоречия не сглажены редактурой | Да, если влияют на решение |
| Открытые вопросы | Нерешенное видно и имеет статус | Нет, если не блокирует предмет review |
| Краткость | Нет пустых или декоративных секций | Нет |

## Problem RFC

| Критерий | Что проверить |
| --- | --- |
| Problem statement | Названы текущее состояние, затронутая сторона и последствие |
| Evidence | Есть evidence либо явно указан план его получить |
| Scope | Определены in scope и out of scope |
| Constraints | Известные ограничения и предположения видны |
| Feedback request | Ревьюер понимает, что подтвердить или оспорить |
| Next decision | Понятен следующий шаг после review |

Не блокируй Problem RFC из-за отсутствия выбранного решения, подробного design или
rollout.

## Product RFC

| Критерий | Что проверить |
| --- | --- |
| Пользователь/система | Понятно, кто или что получает изменение |
| Сценарии | Ключевые happy и material edge scenarios видны |
| Product behavior | Предлагаемое поведение или decision question однозначны |
| Требования | Требования проверяемы и связаны с целями |
| Success criteria | Критерий успеха измерим либо помечен `TBD` |
| Риски | Product, adoption, legal/privacy и operational risks рассмотрены по применимости |
| Rollout | Понятно, как изменение станет доступно и как ограничить ущерб |

## Technical RFC

| Критерий | Что проверить |
| --- | --- |
| Requirements/ASR | Значимые требования и архитектурные драйверы обоснованы |
| Boundaries | Компоненты, ownership и внешние зависимости понятны |
| Alternatives | Реальные варианты описаны симметрично либо объяснено их отсутствие |
| Proposed design | Design или decision question закрывает требования |
| Contracts/data | API, events, data model, consistency и migration покрыты по применимости |
| Failure handling | Timeout, retry, idempotency, partial failure и degradation рассмотрены по применимости |
| Security/privacy | Trust boundaries, authorization и sensitive data рассмотрены по применимости |
| Operations | Observability, capacity, cost и ownership рассмотрены по применимости |
| Delivery | Compatibility, rollout, rollback и migration проверяемы |
| Validation | Test plan, evals и acceptance criteria покрывают значимые риски |

## Combined RFC

Примени Product и Technical gates. Дополнительно проверь:

- нет дублирования problem, goals и risks;
- product behavior отделено от implementation;
- каждое значимое technical decision связано с requirement или constraint;
- product rollout и technical rollout согласованы.

## ADR

| Критерий | Что проверить |
| --- | --- |
| Одно решение | ADR не объединяет независимые решения |
| Status | Решение proposed, accepted, deprecated или superseded |
| Context/forces | Видны причины и ограничения времени принятия решения |
| Decision | Решение сформулировано однозначно и в активном залоге |
| Alternatives | Зафиксированы отклоненные варианты или причина их отсутствия |
| Consequences | Положительные, отрицательные и нейтральные последствия сохранены |
| Supersession | Старые и новые ADR связаны, если решение заменено |

## Критерий ASR

Считай requirement или constraint кандидатом в ASR, если он:

- исключает один или несколько вариантов;
- меняет границы компонентов, ownership или contract;
- определяет consistency, availability, security, privacy или isolation model;
- задает существенный latency, capacity или cost limit;
- создает неприемлемый business, security или operational risk при нарушении;
- потребует дорогой миграции при позднем изменении.

Приоритет сам по себе не делает требование ASR. Объясни механизм влияния.

## Итоговый статус

### Готов к review

Используй, если предмет review сформулирован, все блокирующие критерии закрыты или
имеют достаточные данные для обсуждения, а пробелы не маскируют решение.

### Готов к review с пробелами

Используй, если review может продвинуть документ, но остаются явно перечисленные
неблокирующие пробелы.

### Не готов к review

Используй, если отсутствует предмет review, проблема/context, обязательная граница
профиля или данные, без которых обсуждение будет фиктивным.

Готовность к Problem review не означает готовность к implementation review.

## Правила

- Не выдумывай данные ради статуса `закрыто`.
- Не считай заполненную metadata доказательством согласования.
- Не требуй User Story от чисто технического решения.
- Не требуй числовую метрику, если она неизвестна; фиксируй `TBD`.
- Не публикуй внутренний gate в RFC, если пользователь этого не просил.
