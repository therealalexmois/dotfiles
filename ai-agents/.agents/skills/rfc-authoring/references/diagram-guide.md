## Gate

Добавляй диаграмму, только если она делает хотя бы одно из следующего:

- показывает границу, владение или зависимость, которую легко неверно понять;
- делает видимым порядок, параллельность, retry, timeout или error path;
- фиксирует разрешенные состояния и переходы;
- сравнивает as-is и to-be структуру;
- показывает deployment, trust или network boundary;
- помогает ревьюеру проверить конкретный trade-off.

Одна диаграмма должна отвечать на один вопрос. Перед созданием сформулируй его
одним предложением. Если вопрос не сформулирован, диаграмма, вероятно, декоративна.

## Выбор диаграммы

| Вопрос | Диаграмма | Когда использовать |
| --- | --- | --- |
| Кто взаимодействует с системой и где ее граница? | System context | Новая система, внешние зависимости, роли и ownership boundary |
| Из каких крупных runtime-компонентов состоит решение? | Container/component | Распределение ответственности, зависимости, хранилища и major technology choices |
| В каком порядке выполняется сценарий? | Sequence/dynamic | Несколько участников, async flow, ветвления, retry, timeout или failure propagation |
| Какие состояния допустимы? | State | Lifecycle сущности, job, workflow, feature flag или agent run |
| Где выполняются компоненты? | Deployment | Environments, zones, replicas, load balancers, failover, network и trust boundaries |
| Как движутся и преобразуются данные? | Data flow | Sources, sinks, transformations, sensitive data и retention boundaries |
| Как связаны сущности и cardinality? | ER/data model | Новая схема, ownership, lifecycle и migration данных |
| Как меняется система? | As-is/to-be pair | Структурное изменение, которое трудно оценить по одному to-be виду |
| Как выбирается ветка процесса? | Flowchart/decision flow | Нетривиальные условия с несколькими исходами; не для простого списка правил |

Для большинства архитектурных RFC достаточно system context и container/component
view. Dynamic/sequence view используй точечно для сложного или повторяющегося
runtime-сценария.

## Правила качества

- Назови scope и уровень детализации.
- Подпиши элементы понятными доменными именами.
- Покажи направление и смысл значимых связей.
- Обозначь system, ownership, trust или transaction boundary, если она влияет на
  решение.
- Добавь легенду для нестандартной нотации.
- Покажи error path только если он влияет на design или operational behavior.
- Раздели перегруженную схему по уровням или сценариям.
- Сверь диаграмму с текстом, контрактами и выбранным вариантом.
- Удали деталь, которая не помогает ответить на вопрос диаграммы.
- Для as-is/to-be используй одинаковые имена и сопоставимый уровень масштаба.

## Когда не рисовать

Не добавляй диаграмму:

- для одного простого вызова между двумя компонентами;
- вместо короткого списка требований;
- если она повторяет соседний текст без новой информации;
- если все существенное скрыто в длинных подписях;
- если схема показывает implementation noise, не влияющий на решение;
- только потому, что шаблон содержит раздел `Диаграмма`.

Таблица лучше диаграммы для точного сравнения одинаковых полей. Проза лучше для
одной причинно-следственной связи. Диаграмма лучше для структуры, порядка,
состояний и границ.

## Формат

Сначала используй формат целевого пространства или локального шаблона.

- Mermaid — default для Markdown с поддержкой rendering.
- PlantUML — если wiki или репозиторий использует PlantUML.
- Внешнее изображение — только если source сохраняется рядом и схему можно
  поддерживать актуальной.

Не конвертируй формат ради предпочтения skill. Публикационный слой отвечает за
нативные wiki-макросы.

Основание: C4 рекомендует использовать только полезные уровни; system context и
container views достаточны большинству команд, а dynamic diagrams следует применять
экономно для сложных взаимодействий:
https://c4model.com/diagrams
https://c4model.com/diagrams/dynamic
https://c4model.com/diagrams/deployment
