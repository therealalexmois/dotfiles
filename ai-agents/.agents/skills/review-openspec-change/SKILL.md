# Review OpenSpec Change

Проверять, описывает ли change правильную, проверяемую и реализуемую договоренность до написания кода. Сохранять минимально достаточную строгость: применять официальный базовый gate ко всем change, а расширенный архитектурный и safety-gate — пропорционально риску.

Перед итоговым verdict прочитать [references/review-rubric.md](references/review-rubric.md). Использовать его как рубрику, а не как замену фактам проекта.

Всегда выполнить краткую проверку границы capability. Если change создает, переименовывает, делит или объединяет capability; подходящей base spec нет; имя похоже на change slug, endpoint или отдельное поле; либо выбор области спорный — дополнительно прочитать [references/capability-boundaries.md](references/capability-boundaries.md) целиком.

## Установить источники истины

Проверять источники в таком порядке:

1. Явные требования и подтвержденные решения пользователя.
2. Фактический OpenSpec-контракт проекта: `openspec/config.yaml`, change-local `.openspec.yaml`, resolved schema, templates, artifact rules и релевантные `AGENTS.md`.
3. Актуальные `proposal.md`, все `specs/**/spec.md`, `design.md`, `tasks.md` и base specs, затронутые delta.
4. Код, тесты, протоколы, внешние репозитории и исполнимый runtime evidence для технических утверждений.
5. Официальная документация OpenSpec как базовый контракт фреймворка.

Не выдавать локальную эвристику за требование OpenSpec. При конфликте schema/rules с общими рекомендациями явно назвать конфликт и следовать более конкретному действующему контракту, если он не нарушает явное решение пользователя или безопасность.

## Собрать review-комплект

Найти change самостоятельно, если путь однозначен. Для полного review получить:

- актуальные файлы целиком, а не только summary;
- полный diff относительно согласованной базы;
- `git status --short` для границ изменений;
- resolved schema/config/templates/rules;
- список permanent capabilities с их `Purpose`, релевантные active deltas и точные base specs для проверки `ADDED` / `MODIFIED` / `REMOVED`;
- релевантный код или контракт для спорных factual claims.

Если доступен только diff, проверить измененные участки и явно ограничить verdict; не объявлять весь change согласованным без неизмененных частей. Не требовать повторно данные, уже доступные в репозитории или приложенных файлах.

Если review выполняется без доступа к project worktree и приложенных материалов недостаточно для проверки capability или base contract, прочитать [references/off-repo-review.md](references/off-repo-review.md) целиком. Использовать этот режим только как fallback: не запрашивать уже доступные данные и не выдавать `PASS`, пока target capability и base contract не проверены. Если нужен repo-wide поиск, вернуть готовый к запуску read-only evidence prompt, а не только перечень недостающих данных.

Определить точную команду валидации по установленной версии OpenSpec. Использовать `openspec validate --all --strict --no-interactive`, когда она поддерживается; иначе проверить `openspec validate --help` и выполнить эквивалентную strict non-interactive команду. Всегда запускать `git diff --check`, если доступен Git-worktree.

## Провести review по зависимостям

### 1. Proposal

Проверить один ясный intent, актуальную ценность, узнаваемый scope и явные non-goals. Остановить downstream approval, если proposal решает другую проблему, разросся или остается двусмысленным.

Не требовать mutable Jira/process state или деталей адаптера, если их явно не требует schema. Оставлять в proposal только такие prerequisites, которые материально определяют scope или delivery boundary; механизм и проверку переносить в design/tasks.

### 2. Capability boundary и baseline-стратегия

До проверки текста requirements определить, к какой долгоживущей capability относится изменение. Не считать имя change именем capability по умолчанию: change — единица работы, capability — устойчивая логическая область поведения, в которую после archive попадут requirements.

Проверить:

- существует ли подходящая capability по смыслу, а не только по совпадению имени;
- соответствует ли выбранная область feature area, component или bounded context, понятному команде;
- не является ли имя снимком текущего change, версии endpoint, одного DTO или поля без самостоятельного жизненного цикла;
- не превращена ли capability, наоборот, в общий catch-all для несвязанных владельцев, акторов и инвариантов;
- сможет ли соседнее поведение естественно попасть в эту capability без переименования или размывания Purpose;
- совпадают ли путь delta и фактическая target capability; корректно ли выбран тип delta против ее base requirements.

Не объявлять capability уровня endpoint или поля ошибкой автоматически. Она допустима, если выражает самостоятельный поведенческий контракт с устойчивыми владельцем, потребителями, инвариантами или жизненным циклом. Если имя менялось бы при техническом rename поля или URL без изменения смысла системы, это сигнал слишком низкой гранулярности.

Для brownfield-проекта не требовать отдельный полный baseline перед реальным change. Если подходящей capability нет, текущий change может создать ее через `Purpose` и `ADDED Requirements`, описав только затрагиваемый срез. Не предлагать backfill всего компонента без отдельной ценности. Если уже есть несколько узких соседних specs, отделять необходимую для текущего intent правку от необязательной taxonomy-консолидации; не расширять change автоматически.

Фиксировать capability finding как `MAJOR` только когда неверная граница создает конкурирующий source of truth, неправильный delta/archive result, неоднозначную реализацию или существенное scope-смешение. Maintainability-проблему без влияния на текущую однозначность оценивать как `MINOR` или `SUGGESTION`.

### 3. Delta specs

Считать specs сердцем review. Для каждого requirement проверить:

- одно наблюдаемое поведение и один нормативный `SHALL`/`MUST`;
- хотя бы один конкретный scenario, реально проверяющий requirement;
- важные edge/error cases, а не только happy path;
- отсутствие implementation details, Jira и временного process state;
- корректный тип delta относительно base spec;
- `## Purpose` для новой capability, если она еще не существует.

Проверять, был бы пользователь доволен, если система реализует ровно это и ничего больше. Scenario не должен маскировать расплывчатый или составной requirement.

### 4. Design

Проверять design только в объеме, оправданном размером и риском change. Убедиться, что он объясняет `how`, а не переписывает target behavior:

- решения связаны с requirements и ограничениями;
- значимые альтернативы и trade-offs рассмотрены;
- trust boundaries, enforcement, evidence и residual risks не смешаны;
- factual claims подтверждены ссылкой на код, контракт или runtime output;
- assumptions и неизвестное названы явно;
- rollout, migration, rollback/fallback присутствуют, когда риск этого требует;
- открытые решения имеют владельца и ясно блокируют только затронутый delivery stage.

Не требовать архитектурной церемонии для малого change. Не позволять design создавать observable behavior, которого нет в spec.

### 5. Tasks

Проверить, что задачи идут в разумном порядке, трассируются к requirements/design, атомарны, исполнимы и не расширяют scope. Требовать конкретные пути и команды только там, где они известны и стабильны; не поощрять выдуманные placeholders.

Проверить задачи на реализацию, focused tests, contract/eval coverage, документацию и необходимые delivery gates. Для prerequisite указать наблюдаемые условия снятия и разделить владельцев. Не смешивать статусы локальной реализации, merge, enablement/deploy и archive.

### 6. Сквозная согласованность

Сопоставить intent → requirements/scenarios → design decisions → tasks/tests. Сверить точные имена, allowlists, flags, actors, default behavior, failure semantics и границы scope по всем артефактам.

Отдельно искать:

- поведение, появившееся только в design/tasks;
- capability path, Purpose или taxonomy-решение, расходящиеся между artifacts и archive target;
- requirement без реализации или тестовой задачи;
- task без requirement;
- ложную гарантию, основанную только на названии, комментарии, audit-note или доверии к источнику;
- неподтвержденный внешний контракт;
- противоречие между semantic readiness и delivery readiness.

## Исследовать неизвестное до объявления blocker

Не превращать доступный для проверки факт в вопрос пользователю. Читать доступный репозиторий, искать реализацию и тесты, а при необходимости получать runtime output.

Использовать `/opsx:explore` как исследовательский этап, когда известна проблема, но не решение; требуется сравнение вариантов; неясен scope; либо нужно изучить доступную кодовую базу. Помнить: Explore сам не создает change, артефакты или production-код. Его вывод — гипотеза и evidence trail, а не автоматическое снятие blocker. Для снятия контрактного blocker требовать тот наблюдаемый контракт, который зафиксирован в change.

Отделять:

- подтвержденный факт;
- вывод из фактов;
- принятое решение;
- неизвестное;
- внешний prerequisite.

Если факт недоступен или выбор действительно меняет решение, вернуть `BLOCKED` с одним конкретным вопросом. Не выдумывать решение и не прятать неизвестное за формулировкой «доверенный источник».

## Классифицировать findings и не двигать gate

Использовать уровни из reference-рубрики. Поднимать только проблемы, способные изменить реализацию, безопасность, проверяемость или scope. Не блокировать approval вкусовыми правками.

Для повторного review вести стабильный ledger: ID, severity, evidence, требуемая правка, success condition, status. Проверять исправление и регрессии, но не открывать ранее принятые решения без нового evidence. Новое замечание после нескольких раундов допустимо только как реальный ранее пропущенный дефект или регрессия; назвать, почему оно появилось сейчас.

Считать OpenSpec review пройденным, когда нет внутренних `BLOCKER` и `MAJOR`. Внешний delivery prerequisite может оставить `OpenSpec review = PASS`, одновременно блокируя merge или enablement. Strict validation подтверждает только структурную корректность.

## Вернуть результат

Начинать с одного verdict:

- `PASS` — план семантически готов;
- `PASS с внешним delivery-blocker` — план готов, но явно названная внешняя зависимость блокирует конкретные стадии;
- `CHANGES REQUIRED` — есть внутренние BLOCKER/MAJOR;
- `BLOCKED` — отсутствует необходимый факт или human decision.

Далее дать только полезные разделы:

1. Findings по убыванию severity. Для каждого: ID, точный файл/якорь, evidence, impact, обязательная правка, проверяемое условие закрытия.
2. Capability decision, если граница создается или оспаривается: target path, статус `existing`/`new`/`migration`, краткое основание и отдельно необязательные taxonomy follow-ups.
3. Краткий статус каждого артефакта.
4. Результаты validation и ограничения воспроизводимости.
5. Раздельные статусы OpenSpec review, локальной реализации, merge, enablement/deploy и archive, когда они различаются.
6. Что прислать или сделать дальше — только если действительно требуется.

Не пересказывать все хорошие части при `CHANGES REQUIRED`; назвать подтвержденные сильные стороны кратко. При `PASS` прямо завершить review-loop и не добавлять новый раунд необязательных улучшений.

## Подготовить fix-prompt или bounded loop

Если пользователь просит follow-up prompt, включить только открытые findings, уже принятые решения, ограничения, команды проверки и обязательный формат evidence. Не просить агента пересмотреть закрытые решения.

Если повторные раунды зациклились, сформировать bounded self-review loop:

- определить конечный success condition как отсутствие внутренних BLOCKER/MAJOR;
- перечислить измеримые критерии по текущим findings;
- потребовать полный повторный review всех артефактов после каждой правки;
- потребовать фактический diff и результаты команд, а не summary;
- ограничить число turns/итераций;
- остановиться `BLOCKED` при новом human decision или недоступном факте;
- сохранить внешний delivery-blocker, если он не является дефектом самого OpenSpec.

Не разрешать loop менять production-код, Jira, commits или внешние системы без отдельной авторизации пользователя.
