## Выбор типа

| Тип | Задача читателя | Основа |
|---|---|---|
| Tutorial | Научиться на завершенном примере | Один управляемый путь |
| How-to | Решить конкретную задачу | Условия, шаги и проверка |
| Reference | Найти точный контракт | Полнота и единообразие |
| Explanation | Понять причины и модель | Связи, границы и компромиссы |
| Troubleshooting | Диагностировать сбой | Симптом, причина, проверка, исправление |
| Runbook | Выполнить операционную процедуру | Триггер, действия, контроль и escalation |
| Release notes | Понять изменение | Влияние, совместимость и действие |

Не смешивать несколько задач в одном потоке. Сослаться на отдельный документ,
если читателю нужен другой тип материала.

## Tutorial

- Назвать достижимый результат в начале.
- Провести по одному надежному пути без обзора всех вариантов.
- Дать минимум объяснений, необходимый для движения вперед.
- Показывать наблюдаемый промежуточный результат после значимых шагов.
- Завершить работающим результатом и следующим материалом.

## How-to

- Назвать реальную цель, а не операцию интерфейса.
- Указать применимость и prerequisites.
- Дать только необходимые шаги в порядке выполнения.
- Поставить условие перед ограничиваемым им действием.
- Добавить проверку результата и значимые исключения.

## Reference

- Следовать структуре описываемой системы.
- Описывать однотипные сущности в одинаковом порядке.
- Указывать точные имена, types, required fields, defaults, ограничения, ошибки
  и совместимость, если они известны.
- Отделять нормативный контракт от примеров и объяснений.
- Оптимизировать страницу для поиска факта, а не последовательного чтения.

## Explanation

- Начать с вопроса `почему` или модели, которую нужно понять.
- Объяснить причины, связи, границы и последствия решения.
- Отделить факты системы от интерпретаций и рекомендаций.
- Использовать пример для прояснения модели, а не как универсальное
  доказательство.

## Troubleshooting

- Использовать наблюдаемый симптом как входную точку.
- Начать с безопасных и вероятных проверок.
- Для каждой причины дать способ подтвердить или исключить ее.
- Отделить диагностику от исправления.
- Предупредить перед потерей данных или необратимым действием.
- Завершить проверкой восстановления и условием escalation.

## Runbook

- Назвать trigger, severity и ожидаемое исходное состояние.
- Указать необходимые access, permissions, dashboards и tools.
- Дать безопасные действия в приоритетном порядке.
- После каждого критического действия дать контрольный сигнал.
- Определить stop conditions, rollback и escalation owner.
- Не подменять расследование причины процедурой восстановления.

## Release notes

- Назвать изменение и затронутых пользователей или системы.
- Описать compatibility, migration и required action.
- Отделить breaking changes, deprecations, fixes и known issues.
- Не пересказывать список commits.
- Не заявлять улучшение производительности или надежности без данных.

## README и FAQ

README может сочетать короткий обзор, quick start и навигацию. Не хранить в нем
полный reference, архитектурное объяснение и все рабочие процедуры.

FAQ использовать для самостоятельных повторяющихся вопросов. Не превращать
плохо спроектированную навигацию в длинный список вопросов. Если ответы образуют
последовательность, создать how-to; если описывают контракт, создать reference.
