# Техническая терминология

## Принцип

Сохраняй точность, а не максимальное количество английских слов. Этот файл -
allowlist и набор правил, а не требование использовать каждый термин.

Оставляй термин, если он:

- является идентификатором, именем продукта, технологии, API или протокола;
- закреплен в проекте;
- точнее русского аналога;
- понятен целевой аудитории;
- явно сохранен пользователем.

### Проектные транслитерации

Транслитерированная калька по умолчанию запрещена (см. «Никогда не писать»).
Исключение - слово, которое проект зафиксировал как термин: имя поля, элемент
глоссария или устоявшееся название сущности. Такое слово сохраняется и не
попадает в `banned-terms.toml`, иначе линтер краснил бы каждый документ проекта.

- `тул` (проект: `tool`) - зафиксировано в Nessy Data Agent: глоссарий
  («task-тул», «allowlist тулов»), поле объявления `tools`.
- `скил` (проект: `skill`) - там же: поле объявления `skills`, реестр скилов.

Вне проекта, который их закрепил, предпочитай `инструмент` и `навык`.

## Русская конструкция

Не склоняй английский термин через дефис и не создавай гибридные определения.
Не переводи фразу пословно и не сохраняй иностранный порядок слов. Сначала
восстанови субъект, действие и связь понятий, затем собери естественную русскую
фразу. Не изменяй зарегистрированное название, цитату или идентификатор ради
грамматики.

Плохо:

```text
skill-ом
workflow-а
Router-компонент
backend-сервис
runtime-ом
reviewer-а
preload-ится
skill-реализация
execution-среда
```

Лучше:

```text
с помощью skill
для workflow
компонент Router
backend
в runtime
автор review или проверяющий
загружается заранее
реализация skill
среда выполнения
```

Переписывай составные кальки:

```text
read-only endpoint -> endpoint только на чтение
backend-owned skill -> skill на стороне backend
post-deploy checks -> проверки после деплоя
request-scoped provider -> provider на время запроса
model-facing tool -> tool, доступный модели
production-grade решение -> решение с указанными критериями готовности к production
```

Не заменяй гибрид механически. Выбери конструкцию по смыслу: `отдельный
runtime`, если компонент развивается отдельно; `изолированный runtime`, только
если изоляция является проверяемым свойством; `среда выполнения`, если
английский термин не связан с названием или контрактом.

Допустимы закрепленные сложные слова вроде `HTTP-запрос`, `API-клиент`,
`SRE-команда` и `CI/CD-конвейер`. Правило направлено против искусственного
склонения и кальки, а не против любого дефиса рядом с техническим термином.

## Естественный инженерный регистр

Технический текст не должен становиться сложнее ради профессионального
звучания. Сначала восстанови предметный смысл, затем выбери термин.

```text
Было: Техническая сложность заключалась в превращении неявных личных приемов в
исполняемый стандарт для разных agent harness.
Стало: Нужно было описать личные практики работы с AI-агентами и адаптировать
их для Codex и Claude Code.

Было: Runtime получил специализированный execution-контур с model-facing
ограничениями.
Стало: Для агента выделили отдельный runtime и ограничили данные, которые
передаются модели.
```

Проверяй слова и сочетания:

- `внешняя контрибуция` - обычно внесение изменений внешней командой;
- `межкомандная контрибуция` - обычно межкомандная разработка;
- `корректирующие задачи` - задачи по итогам postmortem, если это их источник;
- `каноническое описание` - описанные или согласованные правила, если речь не
  идет о формально каноническом представлении;
- `согласовать идентичности` - сопоставить пользователей или учетные записи;
- `практические критерии результата` - признаки успешного результата;
- `исполняемый стандарт` - описанный и автоматизированный процесс, если
  автоматизация действительно есть;
- `стабильно в production` - работает в production; стабильность заявляй только
  по известным метрикам или периоду наблюдения;
- `закрыл боль` - решил названную проблему;
- `почистил код` - укажи, что удалено или переработано;
- `снес слой` - удалил слой.

Это контекстные подсказки, а не таблица автоматических замен. Не переводи
официальное название `Evidence Registry`, имя раздела, поле или закрепленный
термин. В обычной прозе используй `артефакты` или `подтверждающие материалы`,
если именно это обозначает `evidence`.

## Использовать русский эквивалент

Если точность не страдает, пиши:

```text
draft -> черновик
request -> запрос
scope -> границы задачи
controlled -> контролируемый
dispatch -> отправка, передача или публикация
owner -> владелец, если это не формальная роль
```

## Никогда не писать

Жесткий стоп-лист: транслитерированные кальки, у которых есть точный русский
эквивалент. В отличие от allowlist выше, это не сигнал для оценки, а запрет.
Замена обязательна во всех жанрах. Оставляй слово, только если пользователь
сохранил его явно или это зафиксированное в проекте название, идентификатор или
цитата.

Единый источник правды - `references/banned-terms.toml` (термин, основы, замена).
Не дублируй список здесь: он проверяется детерминированно линтером
`scripts/lint_banned_terms.py`, который вырезает код, frontmatter и URL и ищет
запрещенные основы только в прозе.

Прогон по редактируемым файлам:

```sh
uv run scripts/lint_banned_terms.py FILE.md
# За корпоративным прокси добавляй --system-certs (uv перепроверяет индекс).
```

Ненулевой код возврата и строки `path:line:col: id -> replacement` означают, что
основу нужно заменить. Чтобы завести новый запрет, добавь `[[term]]` в
`banned-terms.toml`; skill и линтер подхватят его из одного места.

## Никогда не переводить

- имена файлов и пути;
- классы, функции, методы, поля и переменные;
- HTTP methods, API endpoints и payload keys;
- JSON и YAML keys;
- CLI commands;
- Jira keys;
- метрики, log events, feature flags и environment variables.

Не раскрывай и не заменяй косую черту внутри URL, путей, API endpoints,
идентификаторов и устоявшихся названий вроде `CI/CD`. В обычной прозе используй
союз вместо косой черты, если она связывает понятия.

Проверяй один термин по всему тексту. Не используй несколько названий для одной
сущности ради разнообразия.
