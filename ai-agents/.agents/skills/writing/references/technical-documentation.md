# Техническая документация

## Цель

Помочь конкретному читателю безопасно получить нужный результат, найти точный
факт или понять систему. Не документировать компоненты только потому, что они
существуют.

## Сначала выбрать тип документа

Выбрать один основной тип по задаче читателя:

| Тип | Задача читателя | Основа текста |
|---|---|---|
| `tutorial` | Научиться через завершенный пример | управляемый путь с ожидаемым результатом |
| `how-to` | Решить конкретную рабочую задачу | необходимые действия, условия и проверка |
| `reference` | Быстро найти точный контракт | полное и однообразное описание сущностей |
| `explanation` | Понять причины, модель или компромиссы | связи, причины, границы и альтернативы |
| `troubleshooting` | Диагностировать и устранить сбой | симптом -> причина -> проверка -> исправление |
| `release-notes` | Понять изменение и его влияние | что изменилось -> кого касается -> что делать |

README может сочетать краткий обзор, быстрый старт и навигацию, но не должен
становиться складом всех типов документации.

Если исходник смешивает задачи, в `review` указать конфликт. В `author` и `edit`
оставить один основной тип, а второстепенные сведения вынести в короткие ссылки
или отдельные блоки только при необходимости.

## Контракт перед написанием

Определить:

- основного читателя и его уровень знаний;
- реальную задачу, входную точку и ожидаемый результат;
- поддерживаемую версию, окружение и границы применимости;
- prerequisites, permissions и опасные последствия;
- источник истины для команд, API, параметров и поведения;
- способ проверить результат.

Не выдумывать отсутствующие prerequisites, defaults, ответы API, ошибки,
совместимость и результат команд. Если пробел делает инструкцию опасной или
неисполнимой, запросить один критичный факт. Иначе явно обозначить границу.

## Правила по типам

### Tutorial

- Дать достижимый результат в начале.
- Провести по одному надежному пути без обзора всех вариантов.
- Добавить минимум объяснений, нужный для движения вперед.
- После значимых шагов показать наблюдаемый промежуточный результат.
- Завершить работающим итогом и коротко указать следующий материал.

### How-to

- Назвать реальную цель пользователя, а не операцию интерфейса или компонента.
- Указать, когда инструкция применима.
- Дать только необходимые шаги в порядке выполнения.
- Нумеровать последовательность; не смешивать шаги и справочный перечень.
- Поставить условие перед действием, которого оно ограничивает.
- Добавить проверку результата и только значимые исключения.

### Reference

- Следовать структуре описываемой системы.
- Описывать одинаковые сущности в одинаковом порядке.
- Для API и конфигурации сохранять точные имена, типы, обязательность,
  defaults, ограничения, ошибки и совместимость, если они известны.
- Отделять нормативный контракт от примеров и объяснений.
- Не заменять полноту рекламным или обучающим текстом.

### Explanation

- Начать с вопроса `почему` или с модели, которую нужно понять.
- Объяснить причины, связи, границы и последствия решения.
- Отделить факты системы от интерпретаций и рекомендаций.
- Использовать пример только для прояснения модели, а не как доказательство
  универсального правила.

### Troubleshooting

- Использовать наблюдаемый симптом как входную точку.
- Начинать с безопасных и вероятных проверок.
- Для каждой причины дать способ подтвердить или исключить ее.
- Отделить диагностику от исправления.
- Предупредить перед необратимым действием или потерей данных.
- Завершить проверкой восстановления и условием эскалации.

### Release notes

- Назвать изменение и затронутых пользователей или системы.
- Описать совместимость, миграцию и требуемое действие, если они есть.
- Не выдавать внутренний список commits за пользовательскую ценность.
- Не объявлять улучшение производительности или надежности без данных.

## Структура страницы

- Заголовок должен называть задачу или предмет страницы.
- В начале дать назначение и границы, если они не очевидны из заголовка.
- Использовать описательные заголовки, по которым можно найти нужный фрагмент.
- Держать важные prerequisites и warnings до соответствующего действия.
- Использовать нумерованный список только для последовательности.
- Использовать таблицу для повторяющихся полей и сопоставлений, но не для
  длинной прозы или процедуры.
- Давать ссылки в месте, где они нужны читателю; текст ссылки должен описывать
  назначение перехода.
- Не создавать пустые секции ради шаблона.

## Команды и примеры

- Сохранять команды, код, payload и output без стилистического переписывания.
- Не показывать команду, которую нельзя обосновать переданным контрактом.
- Отделять ввод от результата.
- Делать пример минимальным, но исполнимым в заявленных условиях.
- Использовать последовательные имена и значения во всем примере.
- После примера объяснять только неочевидный результат.
- Не использовать placeholder, похожий на реальный secret или персональные
  данные.

## Review технической документации

Проверять по приоритету:

1. Техническая корректность и соответствие источнику истины.
2. Исполнимость, безопасность и полнота критического пути.
3. Соответствие типа документа задаче читателя.
4. Prerequisites, версии, permissions, ограничения и ожидаемый результат.
5. Порядок шагов, ветвления и способ проверки.
6. Находимость: заголовки, терминология, ссылки и сканируемость.
7. Ясность предложений, краткость и единообразие.

Считать `BLOCKER` неверную или опасную команду, потерю обязательного условия,
неверный контракт и шаг, который нельзя выполнить по тексту. Красивый стиль не
компенсирует эти дефекты.
