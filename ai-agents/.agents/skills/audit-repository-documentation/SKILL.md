# Аудит документации репозитория

Проводи аудит как координатор. Сохраняй актуальные требования и техническую точность.
Сокращение текста не должно снижать его полезность.

Не запускай аудит при запросе создать или оценить сам этот skill.

## 1. Установи границы

1. Определи корень репозитория, `git status`, ветку и применимые инструкции.
   Сохраняй чужие изменения. Согласуй владельца пересекающихся правок.
2. Найди доступные skills для документации, инструкций, редактирования и координации.
   Применяй подходящие. Отсутствие skill не блокирует аудит.
3. Определи агентские платформы по конфигурации и файлам.
   Проверь доступные первичные источники из
   [references/review-criteria.md](references/review-criteria.md).
   Если доступа нет, сохрани непроверенные платформенные конструкции и сообщи об ограничении.
   Не заявляй, что проверил актуальные правила.
4. Найди авторские тексты через `git ls-files`:
   - `README*`, `docs/`, вложенные `AGENTS.md` и `CLAUDE.md`;
   - `.claude/rules/`, skills и их `references/`;
   - декларации агентов, prompts и другие инструкции.
5. Осмотри также неотслеживаемые файлы, явно указанные пользователем.
   Исключи vendored, generated, build и cache по назначению и содержанию, а не только по пути.
6. До правок запиши категорию и число строк каждого файла.

## 2. Инвентаризация без правок

Если доступны субагенты, поручай экономной модели только read-only поиск и классификацию.
Для каждого файла запроси:

- путь, основной тип, аудиторию и scope;
- назначение и предполагаемые проблемы;
- связи с другими файлами;
- рекомендуемое действие и уверенность.

Используй основные категории:

| Категория | Содержание |
| --- | --- |
| Human documentation | Tutorial, how-to, reference, explanation, README |
| Agent instructions | Общие и path-scoped инструкции, declarations, prompts |
| Agent Skill | `SKILL.md`, references, описания scripts и assets |
| Historical or operational record | ADR, changelog, план, отчет, status, migration |
| Mixed/unclear | Смешанные файлы и спорная принадлежность |

Учитывай файл в одной основной категории. Вторичные признаки указывай отдельно.

Самостоятельно проверь классификацию. Сверь спорные утверждения с кодом,
конфигурацией, ссылками и пользователями файла.
Сначала передай инвентаризацию координатору. Затем назначай редакторов.

## 3. Раздели работу

Назначь субагентам непересекающиеся пакеты:

1. Документация для людей.
2. `AGENTS.md`, `CLAUDE.md` и rules.
3. Skills, declarations и prompts.
4. Смешанные и исторические материалы.

Пустые пакеты пропусти. Каждому файлу назначь одного владельца записи.
Связанные дубли и общие ссылки передай одному редактору либо сначала реши их у координатора.

- Для смысловых правок выбирай модель, способную проверять технические выводы.
- Экономную модель используй для механической инвентаризации.
- Передай редактору пакет, исходные требования, применимые инструкции и критерии ниже.

Если субагенты недоступны:

- при явном требовании нескольких специалистов сообщи о блокере **до правок**;
  предложи отдельный последовательный запуск;
- иначе выполни специализированные проходы последовательно с теми же проверками.

Не выдавай последовательные проходы за работу субагентов.

## 4. Редактируй по назначению

Применяй [references/review-criteria.md](references/review-criteria.md) для категории файла.

Перед удалением или переносом:

1. Проверь входящие ссылки, активное использование и уникальные действующие требования.
2. Перенеси актуальные требования из завершенных планов и отчетов в канонический документ.
3. Удали лишний исторический файл, только если у него нет самостоятельной задачи
   или требования хранения. Обнови ссылки.

Не создавай навигацию на старый файл только ради сохранения истории.
Если актуальность спорного содержания не установлена, сохрани его и вынеси решение человеку.

Сохраняй ADR, changelog и эксплуатационные записи с самостоятельной задачей.
Git history не всегда заменяет объяснение решения.

Не меняй код, настройки приложения и поведение системы.
Добавляй схему, только если она проясняет проверенный по коду поток или связь.

## 5. Независимая интеграционная проверка

После правок отдельный проверяющий субагент, если доступен, читает общий diff и затронутые связи.
Координатор принимает решение и устраняет замечания.

Проверь:

- требования и технические утверждения по исходным файлам, коду и конфигурации;
- согласованность корневых и локальных инструкций, отсутствие лишней глобальной загрузки;
- относительные ссылки, якоря, навигацию и пути к references после переносов;
- сохранность единственных источников информации при удалении или объединении;
- отсутствие случайных правок кода и конфигурации;
- `git diff --check` и доступные локальные проверки документации.

Подсчитай файлы и строки до и после по **основным** категориям.
Отдельно укажи добавленные, измененные, перемещенные, объединенные и удаленные файлы.
Перенос учитывай один раз. Строковую дельту считай по исходному и конечному состоянию категории.

Если считаешь токены, назови токенизатор и используй один метод для обеих версий.
Сокращение служит диагностическим показателем, а не критерием успеха.

Не добавляй постоянный отчет об аудите в репозиторий.
В ответе укажи:

- число файлов и изменение объема по категориям;
- измененные пути;
- результаты проверок;
- спорные вопросы для человека;
- непроверенную часть scope, если она осталась.

Не заявляй полное покрытие при непроверенных файлах.
