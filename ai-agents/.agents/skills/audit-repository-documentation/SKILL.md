# Аудит документации репозитория

Проводи аудит как координатор. Сохраняй актуальные требования и техническую точность; не ставь процент сокращения выше полезности. Не запускай аудит репозитория при простом запросе создать или оценить этот skill.

## 1. Установи границы

1. Определи корень репозитория, текущий `git status`, ветку, активные инструкции и правила проекта. Не перезаписывай чужие незакоммиченные изменения; согласуй владельца пересекающихся правок.
2. Найди доступные навыки для документации, редактирования, инструкций агентов, Agent Skills и координации. Применяй подходящие, если они доступны; отсутствие какого-либо навыка не блокирует работу.
3. Определи используемые агентские платформы по конфигурации и файлам проекта. При наличии доступа проверь актуальные первичные источники из [references/review-criteria.md](references/review-criteria.md), включая документацию этих платформ. Если доступа нет, не утверждай, что проверил текущую версию правил; сохрани непроверенные платформенные конструкции и отметь ограничение.
4. Инвентаризируй принадлежащие проекту отслеживаемые текстовые файлы, включая `README*`, `docs/`, вложенные `AGENTS.md` и `CLAUDE.md`, `.claude/rules/`, `SKILL.md` с `references/`, декларации агентов, prompts и иные инструкции. Используй `git ls-files` и осмотри явно указанные пользователем неотслеживаемые файлы. Исключи vendored, generated, build и cache по содержанию и назначению, а не только по имени каталога. Зафиксируй исходное число строк по каждому файлу и его категорию до изменений.

## 2. Инвентаризация без правок

Если платформа предоставляет субагентов, поручай экономной модели только поиск и первичную классификацию в режиме read-only. Для каждого файла потребуй: путь, тип, аудиторию, scope, назначение, предполагаемые проблемы, связь с другими файлами, рекомендуемое действие и уверенность. Категории: human documentation (tutorial/how-to/reference/explanation/README), agent instructions (общие/path-scoped/declaration/prompt), Agent Skill (SKILL/reference/script/asset description), historical or operational record (ADR/changelog/план/отчёт/status/migration), mixed/unclear. Один файл учитывай в одной основной категории; указывай вторичные признаки отдельно.

Проверь классификацию самостоятельно. Сверь неоднозначные утверждения с кодом, конфигурацией, ссылками и пользователями файла. Инвентаризацию сначала передай координатору, затем назначай редакторов.

## 3. Раздели работу

При доступных субагентах назначь непересекающиеся пакеты: (1) документация для людей, (2) `AGENTS.md`, `CLAUDE.md` и rules, (3) skills, declarations и prompts, (4) смешанные и исторические материалы. Пакет без файлов можно пропустить. Для смысловых правок и требований выбирай модель, способную проверять технические выводы; дешёвую модель используй для механической инвентаризации. Каждому файлу назначь одного владельца записи. Связанные дублирующие инструкции и общие ссылки передай одному редактору или сначала реши их на уровне координатора. Передай каждому пакет, исходные требования, применимые инструкции и критерии ниже.

Если субагенты недоступны, а запрос требует именно нескольких специализированных субагентов, сообщи о блокере до правок и предложи отдельный последовательный запуск. Если такого требования нет, выполни специализированные проходы последовательно с теми же проверками. Не выдавай последовательные проходы за работу субагентов.

## 4. Редактируй по назначению

Используй [references/review-criteria.md](references/review-criteria.md) для соответствующей категории. Перед удалением или переносом проверь входящие ссылки, активное использование и уникальные действующие требования. Перенеси действующие требования из завершённых планов и отчётов в канонический документ; затем удали лишний исторический файл и обнови ссылки, если у него нет самостоятельного назначения или требования хранения. Не создавай новую навигацию на такой файл только ради сохранения истории. Если актуальность не доказана, сохрани спорное содержание и вынеси решение человеку. Сохраняй ADR, changelog и эксплуатационные записи, когда они выполняют самостоятельную задачу; Git history не всегда заменяет объяснение принятого решения. Не меняй код, настройки приложения и поведение системы. Схемы добавляй лишь если они помогают понять проверенный по коду поток или связь.

## 5. Независимая интеграционная проверка

После всех правок отдельный проверяющий субагент, если доступен, должен прочитать совместный diff и затронутые связи. Координатор принимает решение и устраняет замечания. Проверь:

- обязательные требования и технические утверждения против исходных файлов, кода и конфигурации;
- согласованность инструкций между корневым и локальными scope, отсутствие ненужной глобальной загрузки;
- все относительные ссылки, якоря, ссылки из навигации и пути к reference-файлам после переносов;
- что удаление или объединение не потеряло единственный источник информации;
- diff на случайные изменения кода и конфигурации; `git diff --check` и доступные локальные проверки документации.

Подсчитай числа файлов и строк по **основным** категориям до и после: добавленные, изменённые, перемещённые, объединённые и удалённые файлы. Перенос учитывай один раз; строковую дельту выводи из исходного и конечного состояния соответствующей категории. Если считаешь токены, назови токенизатор и сравни одинаковым методом. Сокращение — диагностический показатель, не критерий успешности.

Не добавляй в репозиторий постоянный отчёт об аудите. В ответе сообщи число файлов по категориям, перечень изменений по путям, сокращение строк или токенов по категориям, результаты проверок и неоднозначные вопросы для человека. Не заявляй о полном покрытии, если часть файлов осталась непроверенной.
