# Критерии для разных файлов

Учитывай назначение файла и локальные правила.
Если доступна сеть, проверяй первичные источники:

| Предмет | Источник |
| --- | --- |
| `AGENTS.md` | https://agents.md/ |
| Agent Skills | https://agentskills.io/specification |
| Типы документации | https://diataxis.fr/ |
| Технический стиль | https://developers.google.com/style |
| Claude Code: memory | https://code.claude.com/docs/en/memory |
| Claude Code: skills | https://code.claude.com/docs/en/skills |
| Claude Code: subagents | https://code.claude.com/docs/en/sub-agents |

Для другой используемой платформы сначала найди ее официальные руководства.
Проверяй project instructions, rules, skills, memory и субагентов по платформе.

## Документация для людей

1. Определи задачу читателя:
   - обучение: tutorial;
   - выполнение задачи: how-to;
   - поиск фактов: reference;
   - понимание решения: explanation;
   - навигация: README.
2. Разделяй файл, только если смешение задач мешает читателю.
3. Начинай с цели или результата. Используй конкретные термины, активный залог и короткие предложения.
4. Убирай повторы и устаревшие временные статусы. Проверяй утверждения по коду и конфигурации.
5. Сохраняй актуальные ограничения и обоснования из планов и отчетов.
   Переноси их в канонический документ как описание текущего состояния.
6. Не помещай хронологию, завершенные планы и промежуточные отчеты в постоянно читаемые документы.
7. Не удаляй ADR, changelog и migration notes автоматически.
   Проверь их назначение, необходимость хранения и ссылки.
8. Добавляй Mermaid, только если схема проясняет проверенный поток или структуру.

## Инструкции агентов

- Оставляй в `AGENTS.md` и `CLAUDE.md` актуальные действия для их scope.
  Не накапливай статусы и заметки прошлых сессий.
- Удаляй сведения, доступные из кода, только если это не ухудшит выполнение задачи.
- Разрешай противоречия между корневыми и вложенными инструкциями.
  Общие правила держи на общем уровне, локальные - рядом с областью применения.
- Проверяй поддержку и синтаксис path-scoped rules на целевой платформе.
- Переноси редкие повторяемые процессы в skills, если платформа их поддерживает.
- Не дублируй правила в `AGENTS.md` и `CLAUDE.md`.
  Используй импорт, ссылку или symlink только при подтвержденной загрузке на целевых платформах.
  Учитывай различия режимов загрузки.
- Для правила указывай условие, действие и проверку.
  Предпочитай положительную формулировку.
  Сохраняй запрет, если он задает безопасность или существенное ограничение.
- `AGENTS.md` - обычный Markdown. Не требуй frontmatter или структуры `SKILL.md`.

## Agent Skills, декларации и prompts

- Проверяй frontmatter `name` и `description` по актуальной спецификации.
  В `description` указывай действие и условия активации.
- Проверяй исполнимость инструкций, актуальность, ограничения и крайние случаи.
- Выноси детали в небольшие `references/` с прямыми неглубокими ссылками из `SKILL.md`.
  Снижай постоянно загружаемый контекст, сохраняя критические шаги.
- Для declarations и prompts проверяй:
  - формат целевого runtime и scope;
  - trigger и доступные инструменты;
  - зависимости от модели;
  - повторы общих инструкций.
- Не переноси платформенный frontmatter в другой формат по аналогии.

## Исторические и смешанные файлы

Перед переносом, объединением или удалением проверь:

1. Кто читает файл и для какой текущей задачи?
2. Есть ли входящие ссылки и внешние потребители?
3. Где сохранятся актуальные требования?
4. Есть ли политика хранения?

Сохраняй ADR, changelog и migration notes с самостоятельной задачей.
Следуй явной политике хранения.

Завершенный план, старый audit report или progress log без отдельной задачи:

1. Перенеси актуальные требования.
2. Удали файл и входящие ссылки.

Сама ссылка не доказывает необходимость исторического файла.
Для восстановления такого черновика достаточно Git history.

Если принадлежность или смысл спорны, вынеси решение человеку.
Не удаляй содержание на основании недоказанного предположения.
