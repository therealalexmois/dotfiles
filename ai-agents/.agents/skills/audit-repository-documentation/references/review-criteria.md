# Критерии для разных файлов

Перед правками учитывай назначение конкретного файла и локальные правила. Проверяй текущие первичные источники, если доступна сеть:

- AGENTS.md: https://agents.md/
- Agent Skills Specification: https://agentskills.io/specification
- Diátaxis: https://diataxis.fr/
- Google developer documentation style guide: https://developers.google.com/style
- Официальные руководства реально используемых платформ о project instructions, rules, skills, memory и субагентах. Для Claude Code: https://code.claude.com/docs/en/memory , https://code.claude.com/docs/en/skills и https://code.claude.com/docs/en/sub-agents . Для другой платформы сначала найди её текущие официальные руководства.

## Документация для людей

- Определи основную задачу читателя: обучение (tutorial), выполнение задачи (how-to), поиск фактов (reference), понимание решения (explanation) либо навигация (README). Разделяй документ только когда смешение действительно мешает читателю.
- Начинай с цели или результата; используй конкретные термины, активный залог и краткие предложения. Убирай повторения и устаревшие временные статусы. Проверяй утверждения по текущему коду и конфигурации.
- Сохраняй действующие ограничения и обоснования, даже когда они впервые появились в плане или отчёте. Переписывай их как описание текущего состояния в подходящем каноническом месте.
- Хронологию, завершённые планы и промежуточные отчёты не размещай в постоянно читаемой документации. Не удаляй ADR, changelog и migration notes автоматически: они могут объяснять решение или поддерживать миграцию. Проверяй необходимость хранения и ссылки.
- Добавляй Mermaid только если проверенная последовательность, поток или структура заметно яснее в схеме.

## Инструкции агентов

- В `AGENTS.md` и `CLAUDE.md` оставляй конкретные актуальные действия, нужные в соответствующем scope. Не используй их для накопления статусов и заметок прошлых сессий. Сведения, которые легко получить из кода, удаляй только если это не ухудшит выполнение задачи.
- Разрешай противоречия между корневыми и вложенными инструкциями; общие правила держи на общем уровне, локальные — рядом с областью применения. Для path-scoped rules проверь поддержку и синтаксис конкретной платформы.
- Повторяемые процессы, не нужные в каждой сессии, переноси в skills при поддержке платформой. Не дублируй правила в `AGENTS.md` и `CLAUDE.md`; импорт, ссылка или symlink допустимы только при подтверждённой загрузке на целевых платформах. Учитывай разные режимы загрузки этих файлов.
- Пиши, когда применять инструкцию, что сделать и как проверить результат. Положительная формулировка предпочтительна, но явный запрет сохраняй, когда это условие безопасности или существенное ограничение.
- `AGENTS.md` — обычный Markdown; не требуй frontmatter и структуры `SKILL.md`.

## Agent Skills, декларации и prompts

- Для `SKILL.md` проверь frontmatter `name` и `description` по актуальной спецификации. В `description` укажи действие и условия активации. Проверь исполнимость инструкций, актуальность, ограничения и крайние случаи.
- Детали выноси в небольшие `references/` с прямыми неглубокими ссылками из `SKILL.md`; progressive disclosure должно экономить постоянно загружаемый контекст. Не сокращай за счёт критического шага.
- Для деклараций агентов и prompts проверь формат конкретного runtime, scope, триггер, доступные инструменты, модельные зависимости и дубли с общими инструкциями. Не переноси платформенный frontmatter в другой формат по аналогии.

## Исторические и смешанные файлы

- Определи, кто и зачем читает файл сейчас. Проверь входящие ссылки, внешние потребители и сохранность актуальных требований перед объединением, переносом или удалением.
- Если история имеет самостоятельную ценность (ADR, changelog, migration notes), оставь её в понятном месте. Завершённый план, старый audit report или progress log без отдельной задачи после переноса актуальных требований удали и убери входящие ссылки. Существующая ссылка сама по себе не делает исторический отчёт нужным. Git history достаточно для восстановления такого черновика. При явной политике хранения сохрани файл в предусмотренном месте.
- При неясной принадлежности или противоречии поставь файл в список решений человека. Не превращай неопределённость в уверенное удаление.
