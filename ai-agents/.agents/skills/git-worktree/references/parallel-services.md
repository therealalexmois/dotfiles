# Параллельные сервисы в worktree

Использовать этот workflow, только если пользователь просит одновременно запустить сервисы из нескольких worktree или правила репозитория требуют отдельные порты и ресурсы. Обычное создание worktree не должно резервировать порты, запускать контейнеры или создавать служебные файлы.

## Установить контракт сервисов

До записи определить:

- точную worktree и task branch;
- сервисы, которым нужны отдельные порты;
- base port и stride из правил репозитория, конфигурации проекта или явного запроса;
- имя проекта Docker Compose, если репозиторий использует Compose;
- команды запуска и проверки из документации репозитория.

Не считать `app=3000`, `PostgreSQL=5432` или `Redis=6379` значениями по умолчанию для любого репозитория. Если порты или stride нельзя получить из локального контракта, задать один блокирующий вопрос.

Не копировать `.env*` автоматически. Локальные файлы попадают в worktree только через `.worktreeinclude` или repository setup script. Не устанавливать зависимости вне существующего setup workflow.

## Выделить порты

1. Получить Git common directory для выбранного репозитория:

   ```sh
   git_common=$(git -C "$worktree_path" rev-parse --path-format=absolute --git-common-dir)
   state_dir="$git_common/agent-worktree-services"
   lock_dir="$state_dir/.allocation.lock"
   ```

2. Создать `$state_dir`, затем получить lock через атомарный `mkdir "$lock_dir"`. Если каталог уже существует, остановиться с blocker и показать его путь. Не ждать в цикле и не удалять чужой lock автоматически.
3. Удерживать lock во время чтения записей, выбора slot, проверки реальных портов и атомарной записи результата. Освободить собственный lock через `rmdir "$lock_dir"` при любом штатном завершении или ошибке. Изменение и удаление записей также выполнять под этим lock.
4. Читать записи только из `$state_dir` и только для worktree, которые все еще зарегистрированы в этом репозитории. Не сканировать другие репозитории или домашнюю директорию.
5. Выбрать минимальный свободный slot `n >= 0`. Для каждого сервиса вычислить `port = base_port + n * stride` и проверить диапазон `1..65535`.
6. Проверить наличие `lsof`. Его отсутствие считать blocker, если repository-local workflow не задает другой способ проверки.
7. Проверить каждый TCP port в реальной системе:

   ```sh
   lsof -nP -iTCP:"$port" -sTCP:LISTEN
   ```

   Код `1` без вывода означает, что listener не найден. Другую ошибку считать blocker. Для UDP использовать отдельную проверку `lsof -nP -iUDP:"$port"`, только если она нужна сервису.
8. Если port занят внешним процессом или другой записью, перейти к следующему slot. Не завершать процесс и не останавливать контейнер автоматически.
9. После проверки атомарно записать результат в `$state_dir/<branch-hash>.json`: сначала создать временный файл в `$state_dir`, затем переименовать его. Получить `branch-hash` через `printf '%s' "$task_branch" | shasum -a 256 | awk '{print $1}'`.

Запись должна содержать `format_version`, абсолютный `worktree`, `branch`, `slot`, объект `ports` и `compose_project`, если он используется. Хранение под Git common directory не добавляет служебные файлы в `git status`.

## Изолировать Docker Compose

Если проект использует Docker Compose, назначить выбранной worktree отдельное project name. Получить его из правил репозитория или составить из имени репозитория и task branch, затем привести к допустимому для проекта формату. При автоматическом построении добавить короткий suffix из `branch-hash`, чтобы разные исходные имена не совпали после нормализации.

Перед запуском показать точное имя. Передавать его явно в каждую команду:

```sh
(cd "$worktree_path" && docker compose -p "$compose_project" up -d)
(cd "$worktree_path" && docker compose -p "$compose_project" ps)
```

Порты передавать способом, который уже поддерживает репозиторий: через разрешенные environment variables, Compose override или setup script. Не создавать новый `.env` и не менять tracked Compose-файлы без отдельного запроса.

## Проверить и очистить

После запуска проверить только выбранные ресурсы:

- `(cd "$worktree_path" && docker compose -p "$compose_project" ps)`, если используется Compose;
- listeners на выделенных портах;
- соответствие записи выбранной worktree и task branch.

Перед cleanup прочитать запись выбранной worktree. Если ее Compose project работает, остановить cleanup с точным blocker. Для процесса на выделенном порту получить PID из `lsof` и проверить его рабочую директорию через `lsof -a -p "$pid" -d cwd`. Блокировать cleanup, только если процесс зависит от выбранной worktree или принадлежность нельзя безопасно установить. Не выполнять `docker compose down`, `kill` или удаление записи без отдельного запроса пользователя.

После подтвержденной остановки сервисов удалить только запись выбранной worktree. Не удалять записи других worktree и не считать отсутствие записи ошибкой.

## Ответ

Если этот workflow применялся, добавить к основному ответу:

```md
- Services: <reserved|running|released|blocked> - <compose project or none>; <service=port list>
```

При конфликте назвать занятый port, найденный listener или Compose project и непримененный шаг.
