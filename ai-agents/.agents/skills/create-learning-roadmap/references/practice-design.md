# Practice design

## Principle

Practice must provide evidence of capability. Reading, watching, copying a tutorial, or vaguely "experimenting" is not sufficient.

## Practice ladder

Choose the smallest useful progression:

1. **Recall/explanation** — Reconstruct the model without the source.
2. **Bounded application** — Apply one concept with narrow constraints.
3. **Diagnosis** — Find a defect, false assumption, or weak solution.
4. **Decision** — Compare alternatives against explicit criteria.
5. **Integration** — Combine adjacent nodes in a mini-project.
6. **Transfer** — Solve an unfamiliar problem without a supplied template.

Do not require every rung for every node. Use the whole ladder across the roadmap.

## Task contract

Every task states action, constraints, deliverable, allowed assistance, objective or rubric-based checks, and relationship to one or more learning outcomes.

## Assistance policy

Specify one:

- closed book;
- official documentation allowed;
- search allowed but no generated solution;
- AI allowed for review after submission;
- unrestricted tools with a required decision log.

Avoid making AI prohibition universal. Match it to what the task is intended to measure.

## Capstone

When appropriate, build one progressive capstone. Start with a concrete problem
and name the system or artefact to implement. Define its functional requirements,
constraints, starter scope, final deliverables, and acceptance criteria.

Each stage should add a capability without requiring a rewrite unrelated to
learning. Every milestone states the learner action, related roadmap nodes,
observable deliverable, and pass/fail checks. A learner must be able to start the
project from the capstone brief without inventing the assignment.

## Quality failures

Reject practice that has no observable output, can be completed by copying the linked tutorial, tests tools rather than the target concept, depends on knowledge not yet introduced, lacks a rubric, or is far larger than the learning value justifies.
