# Instruction Contract

## Core principle

Пиши так, чтобы агент мог выполнить инструкцию как алгоритм, а человек мог проверить результат.

Инструкция не является:

- художественным текстом;
- onboarding-документом;
- философским эссе;
- списком пожеланий;
- заменой permissions, hooks, scripts или CI.

## Rule anatomy

Хорошее правило отвечает на применимые вопросы:

1. Когда правило действует?
2. Кто выполняет действие?
3. Что нужно сделать?
4. Над каким объектом?
5. Что запрещено?
6. Что делать при ошибке или нехватке данных?
7. Как проверить выполнение?

Минимальная форма:

```text
Сделай <действие> над <объектом>.
```

Условная форма:

```text
Если <условие>, сделай <действие>.
```

Критичное правило:

```text
Context: <зачем правило существует>.
Rule: <что агент делает>.
Check: <как проверить выполнение>.
```

## Language

- Начинай правило с команды.
- Пиши одно действие в одном предложении.
- Используй прямой порядок слов.
- Используй один термин для одного смысла.
- Дай определение новому термину при первом использовании.
- Удали слово, если оно не меняет behavior.
- Сохраняй английский технический термин, если он точнее русского аналога.

Используй сильные глаголы:

```text
Проверь.
Найди.
Сравни.
Создай.
Обнови.
Удали.
Не создавай.
Спроси.
Остановись.
Верни.
```

Избегай:

```text
Следует учитывать...
Рекомендуется рассмотреть...
Важно понимать...
По возможности...
Сделай качественно...
Не усложняй...
Соблюдай best practices...
```

Замени оценку проверяемым критерием.

## Scope

- Делай только запрошенную работу.
- Не добавляй новую цель без запроса.
- Не создавай artifact без сценария использования.
- Не меняй архитектуру ради локальной правки.
- Если нужен больший scope, назови причину.
- Если расширение не требуется для результата, не делай его.

## Priority and conflicts

Зафиксируй precedence, если инструкция входит в hierarchy.

Минимальный принцип:

1. system и safety rules;
2. явный пользовательский запрос;
3. project rules;
4. scoped rules;
5. defaults и examples.

Если правила конфликтуют:

1. Назови конфликт.
2. Выбери правило с большим priority.
3. Не смешивай несовместимые требования.
4. Если priority неясен, задай один вопрос.
5. Если вопрос невозможен, выбери безопасное минимальное действие.

## Source policy

Укажи:

- разрешенные источники;
- запрещенные источники;
- правила freshness;
- поведение при conflict;
- запрет на guessing.

Не используй example как current state.
Не считай отсутствие данных разрешением на выдумывание.

## Tool policy

Для каждого tool определи:

- trigger;
- purpose;
- required input;
- error behavior;
- prohibited use.

Правила:

- Не вызывай tool ради имитации работы.
- Не вызывай tool без нужного input.
- Перед изменением прочитай target.
- После изменения проверь результат.
- Если tool вернул ошибку, не выдумывай успех.
- Если tool недоступен, назови ограничение.

## Write and side-effect policy

Если инструкция разрешает write:

- перечисли allowed targets;
- перечисли forbidden targets;
- укажи confirmation gate;
- укажи duplicate check;
- укажи conflict behavior;
- укажи post-write validation.

Внешний side effect требует explicit confirmation, если trusted automation не определена отдельно.

## Artifact policy

Создавай artifact, если он:

- решает задачу;
- нужен для передачи результата;
- нужен повторно;
- имеет owner или пользователя;
- имеет readiness criterion.

Не создавай artifact, если он:

- содержит промежуточные мысли;
- дублирует существующий файл;
- не влияет на решение;
- не имеет сценария использования.

## Idempotency

- Не создавай duplicate file.
- Не добавляй существующее правило повторно.
- Не запускай завершенную операцию без причины.
- Перед созданием проверь существующие artifacts.
- Перед обновлением прочитай target state.

## Output contract

Укажи:

- тип результата;
- обязательные поля или секции;
- порядок;
- критерий готовности;
- ограничения длины, если они материальны;
- что не нужно возвращать.

Плохо:

```text
Верни полезный результат.
```

Хорошо:

```text
Верни таблицу: проблема, риск, исправление.
```

## Stop condition

Agent должен понимать, когда завершить задачу.

Определи:

- обязательные checks;
- допустимые skipped checks;
- поведение при failure;
- evidence готовности;
- формат сообщения об ограничениях.

## Enforcement boundary

Markdown задает context и decision guidance. Markdown не гарантирует enforcement.

Используй deterministic mechanism для:

- destructive command blocking;
- protected path restrictions;
- mandatory tests;
- secret detection;
- formatting;
- policy checks, которые нельзя нарушить.

Если enforcement отсутствует, не называй правило гарантией.

## Structure

Используй только применимые секции:

1. Purpose.
2. When to use.
3. When not to use.
4. Terms.
5. Inputs.
6. Source policy.
7. Rules или Workflow.
8. Decision rules.
9. Tool policy.
10. Write policy.
11. Guardrails.
12. Output contract.
13. Validation.
14. References.

Не оставляй пустые секции.
Не копируй документацию, которую агент может надежно найти в другом source of truth.

## Smells

Считай проблемой:

- `Vague Guidance` – непроверяемые пожелания;
- `Context Bloat` – нерелевантная информация;
- `Conflicting Instructions` – несовместимые правила;
- `No Verification` – нет проверки результата;
- `No Stop Condition` – agent не знает, когда завершить;
- `Hidden Side Effect` – write не отражен в contract;
- `Missing Fallback` – жесткое правило ломается при ошибке;
- `Duplication` – один rule имеет несколько sources of truth;
- `Stale Platform Claim` – текущее behavior платформы принято без проверки;
- `Human Manual` – объяснение для человека вместо agent workflow.

## Final check

Инструкция готова, если:

- agent понимает trigger;
- agent понимает действие;
- agent понимает запрет;
- agent понимает source и tool policy;
- agent понимает fallback;
- agent понимает output;
- agent понимает stop condition;
- человек может проверить результат;
- одно правило имеет один source of truth;
- context не содержит текста без operational value.
