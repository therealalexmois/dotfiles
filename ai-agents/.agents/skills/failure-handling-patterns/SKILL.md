# Паттерны обработки отказов

Объяснять и выбирать паттерны через конкретный сценарий отказа, защищаемое свойство и условия восстановления. Предпочитать минимально достаточное решение; явная ошибка часто корректнее сложного resilience-механизма.

Перед работой прочитать [references/pattern-selection.md](references/pattern-selection.md).

## Выбрать mode

Явно заданный пользователем mode имеет приоритет.

### `selection`

Использовать по умолчанию, когда нужно объяснить, сравнить или подобрать паттерн для описанного сценария, архитектуры либо реализации.

1. Определить источник отказа и наблюдаемое поведение.
2. Уточнить защищаемое свойство: security, integrity, availability, consistency или bounded resource use.
3. Сравнить цену false allow, false deny, явной ошибки и degraded result.
4. Проверить preconditions кандидатов по reference.
5. Выбрать минимальный паттерн или сочетание паттернов.
6. Указать trade-offs, обязательные условия, наблюдаемость и способ проверки.

Не перечислять весь каталог без необходимости. Если данных недостаточно, задавать только вопросы, способные изменить выбор. Код или конфигурацию изменять лишь по явному запросу пользователя.

Возвращать компактную рекомендацию:

- сценарий отказа;
- рекомендуемый паттерн;
- почему он подходит;
- обязательные условия и риски;
- как проверить поведение.

### `review`

Использовать, когда пользователь просит проверить код, diff, commit range или репозиторий на качество обработки отказов.

#### Границы mode

- Не изменять код, конфигурацию, тесты или документацию.
- Не создавать patch, commit или реализацию исправления.
- Использовать read-only команды и не выполнять project code по умолчанию.
- Не делать `fetch`, `pull` и другие сетевые операции. Использовать локальное состояние репозитория.
- Не расширять scope молча. Читать соседний код только для понимания контракта и call path.
- Не рекомендовать паттерн ради паттерна.
- Отделять подтвержденные дефекты от hardening-возможностей и неизвестных.

Если пользователь одновременно просит review и исправление, вернуть только заключение и указать, что реализацию нужно запускать отдельным turn.

#### Определить scope review

Выбирать scope по запросу пользователя. Явный scope имеет приоритет над автоматическим выбором.

##### Текущие изменения

Использовать для `git diff`, текущей реализации или незакоммиченных изменений.

1. Проверить корень репозитория и применимые `AGENTS.md`.
2. Прочитать `git status --short`.
3. Проверить unstaged diff через `git diff --no-ext-diff --find-renames`.
4. Проверить staged diff через `git diff --cached --no-ext-diff --find-renames`.
5. Прочитать относящиеся к изменению untracked-файлы.
6. Прочитать минимальный окружающий контекст: вызывающий код, контракт зависимости, обработчики ошибок и тесты.

Если пользователь задал commit, branch, base или range, использовать его точно. Не обновлять remote refs. Если diff пуст, сообщить об этом и запросить другой scope; не переходить автоматически к полному аудиту.

##### Переданный код или пути

- Считать переданный код основным источником фактов.
- Для локальных путей читать только заданный scope и необходимый соседний контекст.
- Для snippet не предполагать поведение скрытых зависимостей. Фиксировать вопросы, которые могут изменить вывод.
- Не сканировать остальной репозиторий без явного разрешения.

##### Аудит репозитория

Использовать только по явному запросу найти отсутствующую или слабую обработку отказов.

1. Прочитать инструкции репозитория и определить язык, framework, entrypoints и границы компонентов.
2. Проверить зоны риска: startup и configuration, authorization и policy gates, feature flags, remote clients, database и transactions, cache и defaults, queues и workers, orchestration и cancellation, exception middleware, health checks, deploy и preflight.
3. Использовать `rg` и файловую структуру для поиска error handling, timeout, retry, fallback, rollback, rate limiting и resource isolation.
4. Исключить generated, vendor, build и dependency directories.
5. Для каждого кандидата прочитать полный локальный call path до подтверждения вывода.
6. Перечислить проверенные зоны и ограничения покрытия. Не называть аудит исчерпывающим без доказательств.

##### Scope не указан

Если локальный git diff непустой, проверить текущие изменения. Если изменений нет или текущая директория не является репозиторием, запросить snippet, пути, commit range или явный аудит репозитория.

#### Провести review

Для каждой границы отказа определить:

1. **Источник отказа:** invalid input или configuration, недоступность, timeout, overload, partial side effect, cancellation, crash либо неизвестное состояние.
2. **Текущий контракт:** что видит caller и остается ли состояние согласованным.
3. **Защищаемое свойство:** security, integrity, availability, consistency или bounded resource use.
4. **Цена решения:** что опаснее — false allow или false deny.
5. **Запасной режим:** допустимы ли fallback, failover или отключение необязательной функции.
6. **Условия recovery:** является ли ошибка transient, безопасен ли retry, есть ли deadline и идемпотентность.
7. **Blast radius:** может ли отказ занять общие ресурсы или распространиться на другие компоненты.
8. **Side effects:** нужна ли compensation или Saga после частично выполненной операции.
9. **Наблюдаемость:** видны ли outcome, error class, logs, metrics и alert conditions.
10. **Проверка:** есть ли negative tests, integration tests или fault injection.

Сначала оценивать существующее поведение, затем выбирать паттерн по его preconditions. Не считать отсутствие circuit breaker, retry или fallback дефектом без конкретного failure scenario.

#### Классифицировать findings

- `BLOCKER` — вероятен несанкционированный доступ, повреждение данных, необратимый side effect или другой неприемлемый результат.
- `HIGH` — вероятен production-отказ критичного пути, каскадный сбой или неконтролируемое потребление ресурсов.
- `MEDIUM` — отказ обрабатывается некорректно или неполно, но влияние ограничено.
- `LOW` — hardening, наблюдаемость или тестирование без подтвержденного пользовательского дефекта.

Снижать severity при слабых доказательствах и явно помечать inference. Сортировать findings по severity, затем по ожидаемому влиянию.

#### Вернуть заключение

Вернуть результат на языке пользователя.

```markdown
# Заключение по обработке отказов

## Scope

- Mode: `review`
- Scope: diff | paths | snippet | repository audit
- Проверено: ...
- Не проверено: ...

## Вердикт

`приемлемо` | `нужны улучшения` | `небезопасно`

Краткое обоснование в 2–4 предложениях.

## Findings

### [HIGH] Короткий заголовок

- Location: `path/to/file.py:line`
- Current behavior: ...
- Failure scenario: ...
- Risk: ...
- Recommendation: ...
- Pattern: `fail-closed` + `timeout`
- Verification: ...

## Корректные решения

- Указать существующие решения, которые не нужно усложнять.

## Карта рекомендаций

| Location | Current behavior | Recommended pattern | Priority |
| --- | --- | --- | --- |
| ... | ... | ... | ... |

## Неизвестные и ограничения

- Указать только вопросы и пробелы, способные изменить вывод.
```

Не добавлять пустые секции. Если findings отсутствуют, прямо указать, что в проверенном scope проблем не найдено, и перечислить границы проверки. Не возвращать patch, готовый код или пошаговый implementation plan.
